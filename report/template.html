2. The Flow

The data goes through five stages:

  1. Source: the January 2021 yellow taxi file from the NYC TLC. It is a compressed CSV (yellow_tripdata_2021-01.csv.gz) with 1,369,765 trips and 18 columns, downloaded from the DataTalksClub GitHub release.
  2. Extract: ingest_data.py downloads the file and reads it with pd.read_csv using chunksize=100000. This gives back the file in pieces of 100,000 rows instead of loading all of it at once.
  3. Transform: each chunk is read with a fixed set of types. The pickup and dropoff columns become dates and the ID columns become Int64. The data cleaning itself is done in pipeline.py (section 5).
  4. Load: each chunk is inserted into the yellow_taxi_trips table in Postgres using to_sql.
  5. Serve: after loading, the table can be queried with psql or opened in pgAdmin on port 8085.

What each file does

ingest_data.py is the script that loads the data. It takes the database details (user, password, host, port, database name, table name) and the URL of the file as arguments. When it finishes, it runs SELECT COUNT(*) and compares the result to the number of rows it read, so I know nothing was lost.

The Dockerfile builds an image called taxi_ingest:v001. It starts from python:3.13-slim, installs pandas, SQLAlchemy and psycopg2, and copies in ingest_data.py. This way the script runs the same on any computer with Docker, without installing Python packages locally.

docker-compose.yaml starts two containers on a network called pg-network. The first is pgdatabase, a Postgres 16 database with a volume so the data is kept after a restart. The second is pgAdmin. The usernames and passwords are read from a .env file that is in .gitignore, so they are not in the repository.

Why chunks, Int64 and replace on the first chunk

Chunks: I measured the full month at 264 MB of memory after parsing (with memory_usage(deep=True)). One chunk of 100,000 rows is about 20 MB. Reading in chunks keeps the memory use low and the same size no matter how big the file is, and the script prints a line after each chunk, so I can see the progress.

Int64: four columns (VendorID, passenger_count, RatecodeID, payment_type) have 98,352 missing values. The normal int64 type can't hold missing values, so pandas changes these columns to float (1.0 instead of 1), and Postgres would then create them as double precision. Int64 with a capital I allows missing values and keeps them as whole numbers, so in Postgres they become bigint (Figure 7). Fixing the types also stops different chunks from being read with different types.

Replace on the first chunk: for the first chunk, the script runs df.head(0).to_sql(..., if_exists="replace"). This creates an empty table with the right columns, or clears the old one if it already exists. After that every chunk is added with if_exists="append". Because of this, running the script twice doesn't give double the rows.

6. Answers

Q1: Why does the container reach the DB as pgdatabase, not localhost?

Each container has its own network. Inside the ingestion container, localhost means the ingestion container itself, and there is no database running there. Docker Compose puts both containers on pg-network, and on that network each service can be reached by its name, so pgdatabase points to the Postgres container. localhost:5432 only works from my laptop, because the compose file maps port 5432 of the container to my laptop. I saw this myself: with --host=localhost the container failed with "Connection refused" (section 7), and with --host=pgdatabase it worked.

Q2: Why chunks, and what was wrong with replace for many months?

Chunks are needed so the whole file doesn't have to be in memory. One month is already 264 MB, so a full year would be more than 3 GB, while one chunk is only about 20 MB. The progress is also visible after every chunk.

The problem with replace is that the script replaces the table on its first chunk. If you run it again for February, February's first chunk replaces the table and January is deleted. After running it for 12 months you would only have December in the table, and there is no error to tell you. The fix is to only replace once, on the first chunk of the first month, and append everything else. My ingest_data.py does this: it accepts more than one --url and only replaces before the very first chunk.

Q3: How did you verify your results?

  • After the load, ingest_data.py compares the rows it read to SELECT COUNT(*). Both are 1,369,765, and the script would stop with an error if they were different.
  • pipeline.py checks that rows in minus rows removed equals rows out (1,369,765 - 58,535 = 1,311,230). It then reads the cleaned file again to check it really has 1,311,230 rows.
  • I counted two of the numbers again in SQL, separately from pandas (Figure 13): 98,352 missing VendorIDs and 6,586 bad dates. Both match the pandas numbers.
  • I looked at the profile after cleaning (Figure 12). All pickups are in January, the lowest fare is 0.01, the longest trip is 95.5 miles, every trip has at least 1 passenger and no charge is negative.

7. What Broke

The error: the first time I ran the ingestion container I used --host=localhost, because that is what works when you run the script directly on your own computer. It crashed with psycopg2.OperationalError: connection to "localhost" port 5432 failed, Connection refused (Figure 14).

The cause: inside the container, localhost is the container itself, not my laptop and not the database container (see Q1).

The fix: I ran it on the compose network with --network=pg-network and changed the host to --host=pgdatabase, the name of the database service. Then it loaded all 1,369,765 rows (Figure 15).
