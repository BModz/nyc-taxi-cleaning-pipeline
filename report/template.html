2. The flow, in my words

$flow

Source. The NYC TLC yellow-taxi trip records for January 2021, published as a gzip-compressed CSV (1,369,765 trips, 18 columns) on the DataTalksClub nyc-tlc-data GitHub release.

Extract. ingest_data.py downloads the file and reads it with pd.read_csv(..., chunksize=100_000), which returns an iterator of DataFrames instead of one huge DataFrame.

Transform. Every chunk is read with an explicit schema: the two tpep_*_datetime columns are parsed as timestamps and the ID and count columns use pandas' nullable Int64 type. The quality rules live in pipeline.py's clean(df), described in section 5.

Load. Each chunk is written to the Postgres table yellow_taxi_trips with DataFrame.to_sql. The table is replaced once, on the first chunk, and every chunk after that is appended.

Serve. The data is queried with psql inside the database container, or through pgAdmin at localhost:8085.

What each file does, and why

FileWhat it does
ingest_data.pyCommand-line loader. It takes the database user, password, host, port, database, table and one or more --url values. It downloads each file, streams it in 100,000-row chunks into Postgres and then checks that SELECT COUNT(*) equals the number of rows it read.
DockerfileBuilds the taxi_ingest:v001 image: python:3.13-slim plus pandas, SQLAlchemy and psycopg2, with ingest_data.py as the entrypoint. The loader then runs the same way on any machine, with no local Python setup.
docker-compose.yamlStarts two services on one named network, pg-network: pgdatabase (Postgres 16, with a named volume so the data survives restarts, and a health check) and pgadmin. Credentials come from a git-ignored .env file, so no passwords are in the repository.
pipeline.pyProfiling and cleaning. It reads the same file in chunks, profiles every column, applies clean(df), writes the cleaned rows to data/clean/ and saves the metrics to reports/cleaning_report.json.

Why chunks, Int64, and replace on the first chunk

  • Chunks: the full month is about 1.4 million rows and takes 264 MB of memory once parsed (measured with memory_usage(deep=True)). Reading 100,000 rows at a time keeps memory small and constant, and the progress line printed per chunk shows that the load is moving.
  • Int64: VendorID, passenger_count, RatecodeID and payment_type have 98,352 missing values. NumPy's int64 cannot store NaN, so without a schema pandas silently turns these columns into float64 (for example 1.0 instead of 1), and Postgres creates them as double precision. The nullable Int64 type keeps them as whole numbers with real NULLs, and they arrive as bigint (see the table schema in section 3). Also, a column that is empty in the first chunk could be guessed as a different type in later chunks; a fixed schema keeps every chunk the same.
  • Replace on the first chunk: df.head(0).to_sql(..., if_exists="replace") creates an empty table from the schema alone, so re-running the job starts clean instead of doubling the rows. Every chunk is then added with if_exists="append".

6. Answers

Q1: Why does the container reach the DB as pgdatabase, not localhost?

Every container has its own network namespace, so inside the ingestion container localhost means that container itself, and nothing is listening on its port 5432. Docker Compose puts both services on the pg-network network and runs a DNS server on it that resolves each service name to its container's IP address. So pgdatabase is the address of the Postgres container. From my own PC, localhost:5432 does work, but only because the compose file publishes that port to the host with ports: "5432:5432". I tested this: running the container with --host=localhost fails with "Connection refused" (section 7), and --host=pgdatabase works.

Q2: Why chunks, and what was wrong with replace for many months?

Chunks keep memory flat: only 100,000 rows are in memory at a time, whatever the size of the file. One month already takes 264 MB once parsed, so a year would need over 3 GB at once, while a 100,000-row chunk needs only about 20 MB. Chunks also make the progress visible, and if the load fails, it fails partway through instead of at the very end.

Replace for many months: the script uses if_exists="replace" on its first chunk. If it is run once per month, every run hits a new "first chunk", so loading February drops the table and deletes all of January. After loading 12 months, the table would only hold December, and nothing warns you. The fix is to replace only once, before the first chunk of the first month, and append everything else. ingest_data.py does this by accepting several --url values in one run and keeping a single first_chunk switch across all files. Later months can also be added in separate runs that only append.

Q3: How did you verify your results?

  • Load count: ingest_data.py compares the rows it read with SELECT COUNT(*) after the load: 1,369,765 = 1,369,765. The script stops with an error if they differ.
  • Cleaning arithmetic: pipeline.py asserts that input minus the sum of removals equals output (1,369,765 - 58,535 = 1,311,230), then re-reads the cleaned file and asserts that it holds exactly 1,311,230 rows.
  • Independent cross-check in SQL: I computed two of the pandas numbers again in Postgres with different code. Both match: 98,352 null VendorIDs and 6,586 bad-date rows (rule 2 is the first rule that removes rows, so its count can be compared directly with the raw table).
  • Profile after cleaning: every cleaned column falls inside its rule. Pickups are all in January, the smallest fare is 0.01, the longest trip is 95.5 miles, the fewest passengers is 1, and no charge column is negative.

7. What broke

The error

The first time I ran the ingestion container, I used --host=localhost, the same value that works when the script runs directly on my PC. It crashed with psycopg2.OperationalError: connection to server at "localhost" ... port 5432 failed: Connection refused.

$err

The cause

Inside the container, localhost is the container itself, not my PC or the database container (see Q1). Port 5432 was published on my PC, but the ingestion container cannot see my PC's localhost.

The fix

I ran the container on the compose network with --network=pg-network and pointed it at the service name with --host=pgdatabase. The load then finished, and all 1,369,765 rows were inserted and verified.

$fix

Also: Docker was not running

Before that, the first docker command failed because Docker Desktop was not started (the Docker engine's pipe did not exist). Starting Docker Desktop and waiting for the engine fixed it.
